# 建模星型模式

> 来源：《Agile Data Warehouse Design》第 5 章 “Modeling Star Schemas”，书中第 129–162 页（本 PDF 第 150–183 页）。
> 延续[第二章](第02章-建模业务事件.md)、[第三章](第03章-建模业务维度.md)和[第四章](第04章-建模业务过程.md)的“鲜达”案例。以下业务资料均为自拟，供练习。本章概述由读者填写；案例题的答案也留空。

## 1. 本章概述

> 用一段话说明：BEAM✲ 表为什么还不能直接当数据库设计？本章先核对什么，再把它变成星型模式时要补上哪些设计决定。

- 初稿：
  - 这一章前半部分讲的是偏向于物理建模前的准备工作：敏捷数据分析。包含识别候选数据源、数据探查（剖析）。其中对于事实数据源识别相对清晰（不过在互联网工作来看，有时候是采用日志还是服务端数据仍需纠结），但是维度数据源需要费一番心思，需要找到其权威数据来源而非副本数据，甚至有时候维度数据来源不是唯一的。识别后，需要先将数据导入过来（而非原始数据库查询）做探查，主要是三方面：缺失值、唯一值与频率、数据范围与数据类型。当没有数据源作为支撑的主动DW/BI开发时，则需要与业务团队保持始终一致性，不能信息滞后，同时也可为业务团队提供己方见解。
  - 之后，便是模型评审，为防止评审一言堂，需要每位成员独立为ETL做估期测算最后再综合意见实施
  - 后面大部分内容讲的是星型模式设计及实施。第一个要点是维表代理键设置，防止维表主键因为各种原因发生偏移同时保证代码简洁性（当前有无必要我拿不准？）。第二个要点时缓慢变化维度（SCD）处理，这里只讲了类型1：覆盖历史值，针对CV与FV（固定值）和类型2：跟踪历史，针对HV，这里会体现出代理键的优势（这点我认同）。但是在实际中要考虑历史值的成本问题（？）。
  - 最后是对于事实表建模，包含三种类型
    - TF：事务型
    - PS：周期型
    - AS：累积型
  - 处理好维表代理键、退化维度后，针对事实建模，有如如下三种类型：FA（全可加 任意维度汇总）、NA（不可加）、SA（半可加）。最后依据次绘制增强ER图，并尝试汇总维度（用来建宽表吗？）。最终建议交付事实矩阵模式
  - 在实施层面，建议找寻（或开发）自动化工具做数据探查和ddl自动生成工具
- 核对后修订：
  - BEAM✲ 表记录了与业务人员共同确认的事件、维度和实例，但尚未验证源数据能否支撑这些要求，也未完成表间键和加载规则设计，因此不能直接作为最终的数据库设计。本章先针对近期优先交付的事件及一致性维度寻找候选数据源，确认权威来源，并及早剖析缺失值、唯一值及频率、数据范围等特征；剖析可以在离线副本上进行，以免影响在线系统。随后把来源、数据类型和发现的问题标注回 BEAM✲ 模型，由开发团队估算工作量，再与业务人员评审问题、修订模型和调整交付优先级。若源系统尚不存在，模型也可用来明确将来系统需要提供的数据。
  - 模型核定后，开发团队为维度增加代理键和历史管理字段，将事件表中的维度描述替换为事实表的维度外键，同时保留适合留在事实表中的退化维度。代理键有助于应对业务键变化、多来源业务键、缺失维度值，以及同一维度成员的多个历史版本。固定值（FV）和只要求当前值（CV）通常按 Type 1 覆盖；需要保留历史的属性（HV）按 Type 2 增加版本，但源系统从未记录的过去变化无法凭空还原。离散、周期性和演进事件分别可形成事务事实表（TF）、周期快照（PS）和累积快照（AS）。数量字段还需统一计量单位，并判断其全可加（FA）、半可加（SA）或不可加（NA）；比率通常由可加的组成量在查询时计算。最后分别绘制易读的增强星型图，生成物理表，尽早用真实数据和报表原型检验设计，并以物理数据仓库矩阵记录实际建成的事实表、维度表及一致性维度的落实情况。

## 2. 案例续篇：鲜达的源系统

前几章的事件和维度已经和业务人员对过。开发下一轮报表之前，查到的源系统情况如下。

| 系统 | 能提供的记录 | 和业务说法对不上的地方 |
| --- | --- | --- |
| 订单 | 订单号、订单行、会员号、销售名称、下单门店、标价、下单时间 | 订单号每年从 1 重新编号。近 30 天约 8% 的订单没有支付成功时间。 |
| 支付 | 支付流水、支付账户、实收或实退、到账时间、折扣 | 没有会员号。折扣有时是金额，有时写成“8 折”。 |
| 商品主数据 | 销售名称、仓库 SKU、类别 | 类别在另一张表。部分 SKU 没有类别。销售名称和 SKU 不是一对一。 |
| 会员 | 会员号、当前等级、当前城市、手机号 | 只保留当前值，没有等级和城市的历史。 |
| 履约 | 包裹号、仓库 SKU、出货门店、骑手编号、离店时间、签收时间 | 签收时间经常为空。骑手编号在员工表里找不到。 |
| 门店库存 | 门店、SKU、每晚在库数量 | 没有订单号。补货系统尚未上线，没有收货记录。 |

补充说明：业务人员仍希望比较“当时的会员等级”和“现在的会员等级”，也希望按“区域 → 城市 → 门店”“类别 → 商品”下钻。报表名称他们还没统一。
